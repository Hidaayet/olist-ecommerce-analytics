# Decisions log

Every non-obvious analytical or cleaning decision, with the evidence behind it.
Numbers come from `data/clean/cleaning_log.json` (generated by `src/cleaning.py`).

| ID | Decision | Evidence | Impact |
|---|---|---|---|
| D-01 | **Use `customer_unique_id` as the customer** (never `customer_id`) | 99,441 `customer_id` vs 96,096 `customer_unique_id`; `customer_id` is unique per order | Cohorts, retention and RFM are only valid on `customer_unique_id` |
| D-02 | **Aggregate before joining** (items, payments, reviews are one-to-many per order) | Naive items x payments join gives price sum R$14,209,115 vs true R$13,591,644 = **+4.54%** inflation | Revenue is computed from `order_items` (or pre-aggregated CTEs), never from a raw multi-table join |
| D-03 | **Flag non-sales instead of deleting**: `is_valid_sale = status NOT IN (canceled, unavailable)` | 1,234 orders flagged (625 canceled + 609 unavailable). Of the 775 orders without items, 767 are canceled/unavailable | Revenue/delivery KPIs filter on the flag; raw counts stay reproducible |
| D-04 | **Delivery metrics only for truly delivered orders** (`is_delivered` = status delivered AND delivery date present) | 96,478 delivered; 8 have no delivery date, so 96,470 have metrics | `delivery_days`, `delay_days`, `is_late` are NULL otherwise |
| D-05 | **Late = delivered after the estimated date** (`delay_days > 0`) | 7,826 late of 96,470 = **8.1%**; mean delivery 12.6 days, median 10.2, max 209.6 | Maximum is an outlier: use medians/percentiles alongside means |
| D-06 | **Analysis window Jan 2017 - Aug 2018** (`in_analysis_window`) | Data spans 2016-09-04 to 2018-10-17. Sep 2016: 4 orders, Oct 2016: 324, Dec 2016: 1, Nov 2016 absent; Sep 2018: 16, Oct 2018: 4 | 349 orders outside the window. Excluded from trends/cohorts, kept in the data |
| D-07 | **Reviews: keep latest review per order** | 547 orders had >1 review (99,224 -> 98,673 rows, 551 dropped). 814 duplicated `review_id`s in raw, and `review_id` is still not unique afterward (same ID reused across orders) | Grain is one review per order, so **PK = `order_id`**, not `review_id` |
| D-08 | **Payments kept at row level**, with `is_zero_value` flag | 103,886 rows; 2,961 orders with multiple rows; 9 rows with value <= 0; 3 `not_defined` type | Aggregate per order in SQL only |
| D-09 | **Zip prefixes stored as 5-character text** | Raw CSVs hold them as integers, dropping leading zeros (e.g. 01046 -> 1046) | Required for correct joins to geolocation |
| D-10 | **Geolocation collapsed to one row per zip prefix** (median lat/lng, modal city/state); coordinates outside Brazil dropped | 1,000,163 raw rows -> 19,010 zips. 279,669 exact duplicates after text normalization (261,831 before). 42 points outside Brazil dropped | Makes zip a valid key for the relational model |
| D-11 | **City text normalized** (lowercase, accents removed) in customers, sellers, geolocation | Mixed spellings ("sao paulo" / "Sao Paulo" / "são paulo") | Consistent grouping by city |
| D-12 | **Missing categories -> `unknown`; 2 untranslated categories mapped manually** | 610 products without category; `pc_gamer` and `portateis_cozinha_e_preparadores_de_alimentos` absent from translation (mapped to `pc_gamer`, `portable_kitchen_food_preparers`) | 0 untranslated rows remain; translation table now has 74 rows |
| D-13 | **Product column typos fixed** (`lenght` -> `length`) | Raw column names | Cosmetic, but avoids propagating errors into SQL/Power BI |
| D-14 | **Timestamp anomalies flagged, not removed** (`ts_anomaly`) | 189 orders where approval/carrier/delivery timestamps are out of sequence | Excludable from delivery analysis if they distort results |
| D-15 | **Do not drop the 2 products with missing dimensions** (`has_missing_dimensions`) | Only 2 rows | Irrelevant to the business questions |

## Validation results

All 20 hard checks pass: primary-key uniqueness for all tables, and foreign-key integrity from orders, items, payments and reviews to their parents, plus domain checks (score range 1-5, price > 0, no negative delivery times).

Two informational warnings, kept deliberately:

- 279 customers and 7 sellers have zip prefixes with no coordinates in geolocation. This will leave a small number of unmapped points in the map visuals.
- Items value (price + freight) equals payments within 1 cent for **99.69%** of orders (98,362 of 98,665). The 303 exceptions are explained in D-18.

## Phase 3 decisions

| ID | Decision | Evidence | Impact |
|---|---|---|---|
| D-16 | **Cohort = month of a customer's first valid purchase; retention = share of the cohort ordering again in month N** | Customer is `customer_unique_id` (D-01). Activity is capped at Aug 2018, and 6-month metrics use only cohorts up to Feb 2018 | Avoids understating retention for cohorts without enough follow-up time |
| D-17 | **Repeat purchase measured as a 2nd valid order within 180 days**, for customers whose first order is on or before 2018-02-28 | 2,888 customers have a 2nd order; 31.0% of those place it within 1 day (likely split baskets) | The 1-day group is reported separately because it is not really loyalty |
| D-18 | **Payment mismatches are explained, not corrected** | 303 of 98,665 orders (0.31%) differ from items+freight. 264 paid more (avg +R$11.63), and the rate rises with instalments: 0.01% at 1 instalment vs 0.86% at 7+ (consistent with instalment interest). 39 paid less (avg -R$5.10, none with vouchers) | Revenue stays defined from `order_items`, so interest and discounts do not leak into it |
| D-19 | **Timestamp anomalies stay flagged; stage-duration analysis excludes them** | 189 orders: 166 handed to the carrier before purchase, 23 delivered before the carrier. **158 of the 189 occur May-Aug 2018**, and no seller is dominant | Likely a recent data-capture issue. Impact is negligible (0.2% of delivered orders) |
| D-20 | **Delivery trend for Jul-Aug 2018 is treated as optimistic** (right-censoring: undelivered slow orders are not measured) | Median delivery falls from 13.4 days (Mar 2018) to 7.0 days (Aug 2018) while late % rises to 10.4% | Do not present as improvement without caveat |
| D-21 | **A Python validation bug was found and fixed**: float comparison at the 0.01 boundary reported 99.6% instead of 99.69% | SQL uses exact decimals, Python used floats | Check now rounds to cents before comparing |

## Remaining open questions

- Why is repeat purchasing so low and unrelated to review score? Hypotheses (not tested): one-off purchase categories, no loyalty mechanism, customer identity fragmentation. Phase 4 (RFM, category-of-first-purchase) can narrow this down.
- Did the May-Aug 2018 timestamp anomalies come from a change in how Olist logged carrier handover?


## Phase 4 decisions (segmentation and retention)

| ID | Decision | Why |
|---|---|---|
| D-22 | **RFM: quintiles for Recency and Monetary, a binary rule for Frequency** (1 vs 2+ orders). Snapshot date 2018-09-01 | 97% of customers have exactly 1 order, so frequency quintiles would be noise |
| D-23 | **"Repeat" = a 2nd order placed more than 24 hours and at most 180 days after the first**, for customers whose first order is on or before 2018-02-28 | 31% of second orders occur within a day (split baskets, not loyalty). The stricter rule gives a 1.89% repeat rate, replacing the 3.2% in `05_cohorts_retention.sql` query 5.5, which counted same-day orders |
| D-24 | **`vw_first_order_profile` forces CTE materialization** (`AS MATERIALIZED`) | Without it the view ran for over 2 minutes. With it, 2 seconds |
| D-25 | **Bug found and fixed in query 8.2:** `AVG()` ignores NULLs, and one-time buyers have a NULL `days_to_second`, so the first version averaged over repeaters only (about 45% instead of 1.9%). Fixed with `COALESCE(..., FALSE)` | Always check that a rate lands in a plausible range before trusting it |

## Phase 5-6 decisions (BI model, report, delivery)

| ID | Decision | Why |
|---|---|---|
| D-26 | **Power BI reads a star schema in its own schema (`olist_bi`), built as views** | The report needs no transformations, so the logic stays in SQL where it is testable, and a refresh just re-reads the views |
| D-27 | **RFM segments are computed in Python and stored in `olist.customer_segments`** | One definition of "segment" shared by notebooks and the dashboard, instead of re-implementing it in DAX |
| D-28 | **`dim_customer` has no relationship to `dim_date`** (all-time snapshot) | A customer belongs to many dates. The dashboard states this on the page |
| D-29 | **DAX avoids `review_score <= 2`** and uses `IN { 1, 2 }` | In DAX a blank compares as 0, so the simple form would count orders without a review |
| D-30 | **`kpi_reference` view and `expected_values.md`** let anyone reconcile dashboard cards to the database | The DAX could not be executed here, so verification is built in |
| D-31 | **Database URL read from `.env`** (`src/config.py`) | Avoids shell-specific `set` / `$env:` / `export` syntax and keeps the password out of git |
| D-32 | **`.pbix` is not committed; commit a `.pbit` template and screenshots** | A `.pbix` embeds the licensed dataset |
| D-33 | **Impact sizes in the report are labelled upper bounds or scenarios with stated assumptions** | The data cannot establish cause (no experiments), so claiming forecasts would overstate certainty |
